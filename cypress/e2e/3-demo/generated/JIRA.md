# Подключение Jira и работа с дефектами на демо

## 1. Токен в Jira

Аватар → Profile → Manage account → вкладка **Security** → *Create and manage API tokens* →
создать токен и сохранить его.

## 2. Интеграция на уровне инстанса

**Administration → Integrations → Add integration → Jira Software Cloud**

* Name — любое понятное имя
* Jira site URL — `https://<ваш-домен>.atlassian.net`

Для Jira Data Center / Server в документации отдельная страница — параметры отличаются.

## 3. Интеграция на уровне проекта

**Project settings → Integrations → Add integration**

* выбрать созданную на шаге 2 интеграцию
* указать свой e-mail в Jira и API-токен
* **Test connection** — и только потом сохранять

Опционально: **Project settings → Issues → Create mapping** — маппинг лейбла из тестов
(например `jira`) на трекер, чтобы `allure.issue("PROJ-123")` в коде превращался в живую
ссылку на задачу.

## 4. Проверить до демо

Открыть любой упавший тест → **Link defect** → создать дефект → создать из него задачу
в Jira → убедиться, что задача появилась и ссылка работает в обе стороны.

Если настроены вебхуки, закрытие задачи в Jira автоматически закрывает дефект в TestOps.

# Порядок действий на демо

1. Лонч → **without resolution** — это то, над чем команда должна работать.
2. Открыть первый упавший тест. В карточке видно шаг, на котором упало, сообщение
   и **количество похожих падений**.
3. **Link defect** → имя дефекта.
4. В правиле — регулярное выражение по сообщению об ошибке.
   Для billing-gateway отрезаем случайный `request-id`:

   ```
   .*telecom-billing-service unreachable.*
   ```

5. **View match results** — показать, что правило накрывает все 36 тестов. Документация
   советует целиться в устойчивую часть сообщения и не тащить в регулярку id и таймстемпы —
   это ровно то, что мы делаем вслух.
6. Сохранить дефект → **создать задачу в Jira** прямо из карточки дефекта.
7. Повторить на profile-schema (26) и tariff-cache (20) — быстро, без объяснений.
8. Остались одиночные и флаки → перезапустить их из TestOps → часть починится.
9. Оставшиеся мигающие — **замьютить** (`will be fixed` до даты), чтобы они ушли из
   списка нерешённого.
10. Вернуться в overview: unresolved пусто.

## Что это даёт на следующем прогоне

Новый лонч подхватывает правила автоматически: 36 падений сразу привязываются к
существующему дефекту и не попадают в список работы. Для уже прошедших открытых лончей
есть **Apply defect matchers** — применяет правила задним числом.

Это и есть кульминация: «сто двадцать шесть падений, а разобрать нужно было пять причин».
